# Exact real-project probes

The six baseline manifests contain 13 source/declaration pairs and 24 selected semantic
checks. Use the full pinned roots in [fork-corpus.md](../../docs/fork-corpus.md),
including the focused compiler prerequisites recorded there. They do not establish
whole-project coverage or IDEA parity. The harness derives unique UTF-16 positions
from anchors and checks the recorded source/target text hashes before starting LSP.
Completion queries use the end of the identifier; definitions use its start.

```powershell
$env:KTLSP_CORPUS_WAIT_INDEX = '1'
rtk proxy C:/Users/gummy/scoop/apps/git/current/bin/bash.exe dev/ktlsp-harness.sh corpus --root <corpus>/moshi-1.15.2 --file dev/corpus/moshi-1.15.2.json --bin <immutable-release>/ktlsp.exe --no-build
```

Set `JAVA_HOME` to JDK 17 for the five pinned repositories and JDK 21 for CEM.
Use an explicit isolated harness run/cache directory when collecting comparable
evidence. For the independent oracle, select `KTLSP_PROBE_SERVER=intellij` and
provide `IJLS_PLUGIN`, `IJLS_SERVER`, and `IJLS_JDK` as documented in
[fork-corpus.md](../../docs/fork-corpus.md). Successful import is required.

`target_ranges` adds explicitly reviewed exact declaration ranges to the default
identifier range. Only Gradle's primary-constructor probe currently uses it:
IDEA returns its parameter-list range for a Java constructor call. The target
text hash is mandatory, and every alternative must be nonempty and within the
source's UTF-16 bounds. The result must still name exactly one expected file and
match one exact range. An enclosing range or an extra location fails.

Run the pure boundary checks with:

```powershell
rtk proxy nvim --headless -l dev/corpus_matcher_test.lua
```

## CEM source snapshot and declaration oracles

`cem-working-copy.json` records the user's existing source snapshot, including
uncommitted edits; checking out its HEAD alone cannot reconstruct that snapshot.
Create a disposable copy without editing the original, retaining the queried file
only if its text hash matches the manifest. Its non-Mixin queries depend on Create
and NeoForge Java sources. The normal CEM compiler/artifact tasks must first
materialize the actual dependencies in the copy.

Keep the layout `<corpus>/cem-working-copy` and `<corpus>/source-oracles`. The two
declaration files are oracle text outside the indexed project. Extract the exact
archive entries below; the harness reads them without opening editor buffers.
`target_uri_suffix` accepts an archive or extracted declaration only at the same
qualified source path and exact identifier range.

```powershell
$corpusRoot = 'C:/path/to/disposable/corpus'
$createSources = 'C:/path/to/create-1.21.1-6.0.10-280-sources.jar'
$neoForgeSources = Join-Path $corpusRoot 'cem-working-copy/build/moddev/artifacts/neoforge-21.1.248-sources.jar'
Add-Type -AssemblyName System.IO.Compression.FileSystem
$entries = @(
  @{ archive = $createSources; entry = 'com/simibubi/create/content/kinetics/base/BlockBreakingKineticBlockEntity.java' },
  @{ archive = $neoForgeSources; entry = 'net/minecraft/core/HolderGetter.java' }
)
foreach ($item in $entries) {
  $archive = [IO.Compression.ZipFile]::OpenRead($item.archive)
  try {
    $entry = $archive.GetEntry($item.entry)
    if ($null -eq $entry) { throw ('Missing archive entry: ' + $item.entry) }
    $destination = Join-Path (Join-Path $corpusRoot 'source-oracles') $item.entry
    [IO.Directory]::CreateDirectory([IO.Path]::GetDirectoryName($destination)) | Out-Null
    [IO.Compression.ZipFileExtensions]::ExtractToFile($entry, $destination, $true)
  } finally {
    $archive.Dispose()
  }
}
```

On the originating machine Create's archive is in its versioned Gradle cache;
NeoForge's archive is generated by `createMinecraftArtifacts`. Use the versions
above and retain the manifest's hashes. The hashes cover Neovim `readfile()` lines
joined with `\n`, rather than archive bytes or platform line endings. The harness
rejects a changed source or declaration instead of moving an expected range to
make a result pass. No third-party source archive is stored in this directory.

## Unsaved incomplete-code fixture

`mixed-incomplete.json` is a separate fixture control. Generate the golden with
`nvim -l dev/mixed_project.lua <run>/project`, compile its source in an external
copy as the existing `mixed` scenario does, then run `corpus` against that golden
with this manifest. The `mixed` scenario also generates a suitable compiled
golden under its run directory. All artifacts must remain outside the project.

The ten cases cover partial members, dangling dots, broken peer syntax and
known/unknown receivers in both languages. They make twelve completion requests:
each unknown receiver includes a useful known receiver in the same edited state.
`buffer_edits` replace unique anchors in query or peer files; `definition: false`
selects completion-only cases. `completion_excludes` rejects wrong members, and
`completion_token: false` is permitted only with a positive `known_control`.
An LSP null negative response is distinct from a timeout or protocol error.

The scenario flushes pending Neovim notifications and checks outbound versions
before one response per query, restores each buffer, then verifies the unchanged
disk golden and clean editor buffers. That test transport barrier does not prove
normal editor debounce, server recomputation completion or popup-display latency.

## Real-root incomplete controls

Each `<project>-incomplete.json` uses the same corpus route against its full pinned
root. Five cases make six first-response completion requests: a compiled disk
control, a partial member, a dangling dot, a broken peer, and an unknown receiver
paired with a useful known receiver in the same edited state. Across the six
roots this is 30 cases and 36 requests per engine. A negative result does not pass
its case if the known receiver is unusable. Expectations and recorded IDEA setup
or semantic limitations remain explicit in each manifest and
[fork-corpus.md](../../docs/fork-corpus.md).

```powershell
$env:KTLSP_CORPUS_WAIT_INDEX = '1'
rtk proxy C:/Users/gummy/scoop/apps/git/current/bin/bash.exe dev/ktlsp-harness.sh corpus --root <corpus>/moshi-1.15.2 --file dev/corpus/moshi-1.15.2-incomplete.json --bin <immutable-release>/ktlsp.exe --no-build
```

Query and edited peer hashes are checked before startup. Source edits remain in
buffers, are delivered once before each query, and are restored before the next
case. Peers are attached because they are edited; this differs from merely reading
a definition target as oracle text. Background index counts therefore need to be
read alongside the attached buffers. These selected RPC controls do not establish
whole-root editing coverage, normal debounce behavior or popup latency.

## Compiler-plugin and processor controls

Generate a new disposable Gradle project with the same sources and build settings
as the independently compiled plugin control:

```powershell
rtk proxy nvim --headless -l dev/compiler_plugin_project.lua <new-external-directory>
```

It pins Kotlin JVM, serialization, all-open, no-arg and Kotlin Lombok to 1.9.23,
javac Lombok processing to 1.18.32, serialization core to 1.6.3 and JDK 17.
Compile the generated project with its actual Gradle wrapper before running
`corpus --root <directory> --file dev/corpus/compiler-plugins.json`. Its twelve
completion requests cover generated serialization/getter APIs from Java and
Kotlin in complete, partial and dangling-dot buffers. No generated API is
handwritten into a stub. Enable `KTLSP_CORPUS_WAIT_INDEX=1` for ktlsp's first
response after indexing; retain missing-input coverage failures separately.

Set `KTLSP_UI_CASES` to the absolute path of `compiler-plugins-ui.json` to run
the existing native completion UI probe after the corpus requests. The UI case
checks Kotlin's generated getter property: type a dot, select `name` from the
actual LSP popup and inspect the exact inserted `.name` expression. IDEA offers
this property projection rather than the manifest's literal `getName` method
label; the original method-label failures are retained. The accepted expression
has a compiler-positive processor-on and compiler-negative processor-off control.
Use the same isolated temporary IntelliJ setup as the other corpus scenarios.

The current ktlsp baseline fails all twelve generated-method completion checks.
These fixtures expose that gap; they do not establish plugin configuration
refresh, generated-symbol navigation, diagnostics, KAPT or KSP acceptance.

## Actual KAPT and KSP generated sources

`dev/processor_project.lua` creates three Gradle projects: a Java annotation
processor, a Kotlin KSP processor and their mixed Java/Kotlin consumer. The
processors use the actual Filer and KSP CodeGenerator APIs. It pins Gradle 7.4.2,
Kotlin JVM/KAPT 1.8.21, KSP 1.8.21-1.0.11 and JDK 17. No generated member is
written into the fixture's authored input sources.

```powershell
$processorRoot = 'C:/path/to/new/disposable/processor-project'
$env:JAVA_HOME = 'C:/path/to/jdk-17'
rtk proxy nvim --headless -l dev/processor_project.lua $processorRoot
rtk proxy "$processorRoot/gradlew.bat" --project-dir $processorRoot :app:classes --no-daemon --console=plain
rtk proxy "$env:JAVA_HOME/bin/java.exe" --class-path "$processorRoot/app/build/classes/kotlin/main;$processorRoot/app/build/classes/java/main" "$processorRoot/oracle/RuntimeCheck.java" v1
$env:KTLSP_CORPUS_WAIT_INDEX = '1'
rtk proxy C:/path/to/git/bin/bash.exe dev/ktlsp-harness.sh corpus --root $processorRoot --file dev/corpus/processor-generated.json --bin <immutable-release>/ktlsp.exe --no-build
```

Use `--offline` on Gradle commands after the wrapper, plugins and dependencies
are cached. The runtime control checks six Java/Kotlin calls and the presence
and absence of versioned members on all three generated types, reporting twelve
assertions. `processor-generated.json` requires the default `generationLabel=v1`
output. Its 24 cases make 30 completion requests and six exact declaration
requests: six compiled golden uses, twelve partial/dangling-dot edits and six
unknown receivers, each paired with a useful generated receiver. All edits stay
in buffers and use the existing first-response/delivery checks.

Building with `-PgenerationLabel=v2` replaces `versionOne` with `versionTwo` in
all three generated APIs; the runtime control then takes `v2`. Building
`:app:clean :app:classes -PprocessingDisabled` must fail because all three APIs
are missing. Rebuild the default v1 output before using the pinned manifest.
These compiler/runtime transitions independently establish the expected API.
The corpus probe alone does not establish same-client build-event refresh,
processor-off diagnostics, or extension-provided generated symbols.
